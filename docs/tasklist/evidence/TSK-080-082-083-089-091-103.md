## Task evidence

### TSK-080 — read-only payment projections

- Inventory checkout return URL was requested before callback settlement; booking and payment remained `PENDING_PAYMENT`/`PENDING` and no provider event was created.
- Guest status projection distinguishes hybrid online verified payment from the host balance: `SUCCESS`, online amount 220,000 VND, direct outstanding 880,000 VND, direct receipt `OUTSTANDING`.
- After all provider attempts failed, status reports booking `CANCELLED`, payment/online status `FAILED`, and online verified amount zero. A late valid success is shown as `RECONCILE`, not as accepted/paid, and does not revive the booking.
- Ownership/authentication remains covered by `SecurityConfigTest`; the legacy return-page test independently verifies read-only behavior.
- **Boundary:** refund execution, direct receipts, and a UI consumer for all future outbox states are not included here.

### TSK-082 — verified checkout/IPN lifecycle

- HMAC-signed test callbacks are checked against merchant, VNPAY envelope version/command/result fields, provider reference and the attempt's server-owned due amount/currency.
- Integration cases reject tampered signature, other merchant, and invalid command without recording events; correctly signed wrong currency/amount is reconciled and cannot confirm or terminalize a failed retry.
- Valid hybrid callback confirms all held inventory, accepts exactly one collection and emits one transactional `PAYMENT_CONFIRMED` outbox row. Duplicate callback does not duplicate the accepted collection/outbox; extra payment is reconciliation-only.
- Expiry/IPN race uses real PostgreSQL transactions; late callback after cancellation does not revive inventory. Three terminal failed attempts expire early, release holds and discount reservation, set payment `FAILED`, and create one `PAYMENT_FAILED` outbox row.
- Added V19 `inventory_payment_outbox`; the verified payment/outbox write is part of the same database transaction. Terminal expiry/failure outbox writes are likewise transactional.
- **Boundary:** there is not yet an outbox dispatcher/retry worker; notification delivery/retry belongs to TSK-076. Sandbox config only; no real-money authorization.

### TSK-083 — PostgreSQL inventory invariants

- `InventoryCapacityIntegrationTest` ran 39 PostgreSQL 16 tests, including shared-plan last-unit races, two types on one property, adjacent stays, missing calendar/all-item rollback, capacity reduction vs hold lock ordering, immutable snapshots, and expired-hold transition rules.
- `InventoryCheckoutIntegrationTest` additionally exercised the verified IPN/expiry race and a failed-three-attempt release; no accepted collection or resurrection occurred for late receipts.
- The legacy property exclusion was not removed and no multi-room cutover/backfill is claimed.

### TSK-089 — discount reservation/consumption/funding

- Database race test allows only one reservation under quota=1; successful verified callback consumes once, duplicate provider event does not double consume, and terminal failure releases reservation without incrementing `used_count`.
- Frozen 6.8m fixture verifies 200,000 VND discount, 1,050,000 gross commission, 850,000 net retention, 1,360,000 hybrid due-online, 5,440,000 direct balance, and 510,000 platform-held host payable.
- A discount exceeding the commission funding bound is rejected (`ERR_DISCOUNT_FUNDING`). A 1 VND discount across three nights reconciles exactly to the nightly snapshots with stable remainder allocation; a one-VND hybrid total producing zero online due is rejected before a quote/payment attempt is persisted.
- **Boundary:** campaign publish/quota lifecycle is validated in test DB; no production campaign configuration is inferred.

### TSK-091 — shared stay-date/availability read policy

- `StayDatePolicyTest` verifies HCM same-day 19:59 acceptance / exact 20:00 cutoff, 1- and 30-night boundaries, zero/31-night rejection, and past dates.
- `SearchAvailabilityIntegrationTest` (5 tests) verifies past/too-long rejection, half-open adjacency, conflicting legacy booking exclusion, and date-less indicative results. `PropertyWebIntegrationTest` and inventory offer tests verify live stock/read-only offer response, all-night min-stock, stop-sale, per-room occupancy, and fail-closed calendar.
- Search, offers, quotes, and inventory booking creation use the shared HCM date policy; checkout still revalidates the accepted quote and capacity under the booking transaction.
- The legacy property-level booking exclusion remains intentionally conservative pending cutover; this evidence does not claim inventory search cutover or bypass of that constraint.

### TSK-103 — quote/dual-mode financial composition

- Checkout integration verifies FULL_PREPAY and HYBRID_DEPOSIT against the frozen 7,000,000 room charges / 200,000 discount fixture: total 6,800,000; full due 6,800,000/balance 0; hybrid due 1,360,000/balance 5,440,000.
- Verified hybrid financial snapshot sums match 1,050,000 gross commission, 850,000 net retention, and 510,000 held payable. Two room allocations and nightly room/fee/discount sums are asserted in PostgreSQL.
- A separate two-room fixture checks room charges, cleaning fee, allocations, full/hybrid due/balance, commission/net/held fields; the rounding and insufficient-funding cases are checked as above.
- **Boundary:** no refund, direct-receipt, payout, actual-stay, migration/cutover, or end-to-end production clearance is included.
