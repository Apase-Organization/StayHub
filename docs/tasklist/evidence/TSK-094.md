# TSK-094 — booking terms/listing snapshots

**Status: implementation in progress; independent review/acceptance pending, 2026-10-24.** This records forward capture and read projection for new bookings. It does not backfill unknown historical listing values or change archive/retention policy for records created before V22.

## Delivered

- V22 adds `booking_listing_snapshots`, inserted by a deferred trigger in the booking transaction. It stores a listing snapshot and terms snapshot, including dates, guests, currency, mode, inventory policy/request hash, price/fees/discount/total and the V15 financial snapshot when present.
- Snapshot rows reject update and delete. A stable fingerprint is recorded with each snapshot.
- `BookingMapper` returns frozen title/city/cover where a snapshot exists and projects payment mode, subtotal, due-online and direct host balance from the immutable financial snapshot. Pre-V22 bookings without snapshots use the existing legacy projection; no current data is presented as historical truth.
- `BookingProjectionSmokeTest` changes the property title, city, price and status after booking and verifies booking reads retain the captured title/city and HYBRID_DEPOSIT financial amounts.

## Verification

- `./mvnw -q -Dtest=BookingProjectionSmokeTest test` — PASS, PostgreSQL 16 Testcontainers; 1 test case, 0.614s case time (16.421s suite time including application/container startup).
- The same test verifies a quantity-2 booking creates one review and its immutable email payload carries item-level room quantity/room nights.
- `./mvnw -q -DskipTests compile` — PASS.
- Full-suite, Compose and e2e checks were not run. No production cutover or legal/retention approval is claimed.

## Limits

Private evidence retention/access rules remain governed by TSK-111/TSK-093 and are not changed here. Historical rows with no captured listing, payment mode or consent evidence remain unknown and require an approved migration/reconciliation plan; this task does not infer those values.
