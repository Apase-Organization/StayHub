# TSK-100 / TSK-101 — Sprint 2 read-only offers and guest selection

Shared scope/background record. The task-specific acceptance records are
[TSK-100](TSK-100.md) and [TSK-101](TSK-101.md). Checkout/quote composition remains
owned by TSK-103/082 and is not claimed here.

## TSK-100 — read-only eligible offers

- `POST /api/v1/properties/{propertyId}/availability` returns one property with a
  list of active room-type/rate-plan offers. It does not duplicate property cards
  by room type or rate plan.
- Stock uses the minimum per-night `total - outOfOrder - HELD - CONFIRMED` over
  `[checkIn, checkOut)`. Missing calendar rows fail closed; type stop-sale marks
  the offer unavailable; expired holds still count until lifecycle release.
- All plans on a type read the same type-day pool. Each requested room allocation
  is checked against that type's current adult/occupant limits and child ages.
- With dates, response gives `availableQuantity`, requested room count, server
  nightly price and an explicit stay-total basis (rooms × nights × nightly price +
  one property cleaning fee; tax is currently disabled). Without dates it returns
  `availableQuantity=null`, `totalStay=null`, and `liveAvailabilityChecked=false`.
- Endpoint is read-only, public with CSRF protection, and exposes no guest/booking
  data. Archived or unpriced plans are omitted.

## TSK-101 — guest room selection

- Property detail now collects dates, mode, room count, adult count and child ages
  separately per room. It calls the read-only offer endpoint and presents
  eligible/sold-out alternatives, nightly basis and total stay.
- Changing occupancy/date/mode clears old results and the local selection summary;
  an HTTP 409 asks the guest to search again. No client price is trusted.
- No quote or booking submit is exposed: immutable quote consent/reconsent and
  payment-mode amount composition belong to TSK-103/082. The old MVC booking route
  remains separate and is not sent room type selections.
