## Delivered boundary

Seven additive tables: room_types, rate_plans, type_day_inventory, booking_items,
room_allocations, nightly_snapshots, inventory_commitments. Property sale_mode
remains nullable for legacy rows; explicit type mode is required by composite FK.
Existing property_type remains classification; timezone is HCM only. No historical
mode, finance, prices, allocations or commitments inferred/backfilled.

Composite references enforce booking/property, type/property, plan/type/property,
commitment/item/type/day and snapshot/allocation grain. Plans have no stock.
Quantity/adult/age/ordinal/date/complete allocation and nightly count guards are
enforced in PostgreSQL, including deferred commit checks for graph construction.
Whole-VND uses unconstrained NUMERIC domain + whole/range checks: even 1.001 is
rejected without typmod rounding; maximum 19 whole digits. No binary floats.

Whole-place quantity and daily total are at most one. Conservative identity rule:
only one whole-place type per property **including archived types**, preventing a
replacement pool from double-selling alongside old commitments. The same identity
can archive/reactivate; no need for a new type just to edit occupancy data.
Type scope is immutable, but current max_adults/max_occupants/base_quantity may
change subject to DB checks. Booking items capture max_adults_snapshot and
max_occupants_snapshot under a type SHARE lock at construction, and shape checks
use those immutable rights. New admission checks allocations against current
limits under locks; existing holds retain rights through conversion/release even
after a reduction/archive. Item selection, nightly snapshots and header
property/dates are frozen once referenced. Snapshot DELETE is rejected even in
construction; SQL transaction rollback requires no DELETE and remains supported.

HELD + CONFIRMED sum is the only stock usage, no double counters. Expired HELD
still counts until RELEASED. Day-row write locks serialize admission and OOO/total
changes, with SUM checked under lock. New confirmed rows, quantity/deadline moves,
delete and RELEASED resurrection reject. Conversion uses original rows and checks
authoritative clock after locks; confirmed cancellation may release. Stop-sale
blocks new holds, not conversion. Missing calendar fails closed.

`InventoryCapacityService` internal transactional primitives: holdAll(bookingId,
originalExpiresAt), confirmAll(bookingId), releaseAll(bookingId), and versioned
updateDay(typeId,date,total,outOfOrder,stopSale,expectedVersion). It locks booking,
then **all types sorted by id**, **all plans sorted by id** using FOR SHARE, then
**all** distinct (type,date) rows sorted FOR UPDATE before writes. SHARE conflicts
with non-key status/occupancy updates; KEY SHARE would not. Direct SQL admission
also locks booking -> type SHARE -> plan SHARE -> day, re-reading status after
lock acquisition. Conversion/release do not require ACTIVE status. No implicit calendar
creation. Caller owns authentication/ownership, approved plan restrictions, quote,
idempotency, original hold-deadline provenance and booking/payment lifecycle.
These are not public APIs or a complete checkout/payment implementation. Direct
SQL has DB safety guards but arbitrary reverse-order batch writers may deadlock
and must roll back; production multi-key writers must use the stable protocol.
TSK-098 Host batch changes must use the same type-before-plan-before-day ordering
and type ids sorted; no acquiring an earlier booking lock after type/day writes.
Selection construction must also sort multi-type writes before the service call.

## Migration and rollback review design (not executed uninstall)

Forward: Flyway transactional additive DDL, nullable legacy mode, no data backfill,
new composite unique keys/FKs/triggers/domain/indexes; original
`uq_bookings_active_date_overlap` from V12 remains unchanged for PENDING,
PENDING_PAYMENT and CONFIRMED. No new entities force ORM/schema changes on legacy
models. IDs and existing financial records remain untouched.

Application rollback before cutover: stop new inventory writers; preserve all
new records and keep V14/protection installed; return to legacy application only
with its original exclusion still in place. Do **not** delete new bookings or
drop protections to make rollback look successful. Additive uninstall is only a
reviewed design for an empty, never-activated inventory graph: verify no new
references/data, remove new triggers/functions/tables in reverse dependency order,
then domain/new unique keys/columns. Do not execute blind DROP CASCADE or edit
Flyway history. Once data exists, preserve it and reconcile via a forward migration
and an explicitly approved rollout/rollback plan under TSK-106/108.

Runtime transaction rollback is actually tested: insufficient second item/night
leaves zero commitments, with service transaction boundaries (not mocked logic).
Independent review has now accepted this migration/rollback design, as recorded
above. This is design acceptance, not evidence of a production uninstall run.
